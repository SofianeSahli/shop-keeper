# Research: Shared Catalog and Shop Products

Decisions for `specs/007-catalog-products/plan.md`. Sources: GS1 General Specifications (GTIN check digit, restricted-circulation prefixes), Unicode normalization forms (UAX #15), PHP `intl` `Normalizer`, MySQL 8.4 reference (collations, unique indexes, savepoints), Laravel 13 docs (cursor pagination, nested transactions). Checked 2026-11-07.

## R1. One module, `Catalog`

- **Decision**: A new module `app/Modules/Catalog/` owns `global_products`, `global_product_names`, `global_product_terms` and `shop_products`.
- **Rationale**: The duplicate check (FR-016, FR-017) and the suggestions (FR-014) read the shared catalog and the shop's products in the same query. A module may not read another module's tables, so splitting them would force every search through action calls. Later stock (`Inventory`) and sales modules reference `shop_products` by id only.
- **Alternatives**: `Catalog` plus `Products` modules: rejected for the reason above.

## R2. Current shop

- **Decision**: The Shops module adds a route middleware, alias `shop`, that finds the signed-in merchant's shop id through a new Shops action `FindShopIdOfOwner` and binds an `App\Shared\CurrentShop` value (the shop id) in the container for the request. A merchant with no shop gets `shop.required` (403). Every product route uses `auth:sanctum` then `shop`. Product URLs carry no shop id: `/api/v1/products`.
- **Rationale**: The backend guide puts "current shop" in `app/Shared/`, and the Catalog module must not read `shops`. One shop per merchant (006) makes the shop implicit, and the future sync endpoints (`/api/v1/sync/push`) carry no shop id either.
- **Alternatives**: `/shops/{shop}/products`: a redundant id the server must check against the owner anyway.

## R3. Shop product keys are client UUIDs

- **Decision**: `shop_products.id` is a UUID generated by the client, stored as `BINARY(16)` through a small shared cast (`app/Shared/Database/BinaryUuid`). `POST /products` requires `id`. Sending again an `id` the shop already has returns that product with 200 and changes nothing; an `id` held by another shop is refused as `id.taken` without revealing anything. Version 7 UUIDs are recommended to the app (index locality); any valid UUID is accepted.
- **Rationale**: The backend guide requires client UUIDs for records the app creates offline. The connected-app spec will let a merchant add a product while receiving stock or selling offline, and offline sale lines must point to it. Changing a primary key after sales reference it would be a costly migration. It also makes a network retry harmless (US3-5).
- **Alternatives**: Auto-increment id now, UUID later: rejected for the migration cost.

## R4. Barcodes

- **Decision**: One value object `Barcode::parse(string)`: remove spaces; accept 8, 12 or 13 digits only; check the GS1 mod-10 check digit; turn a 12-digit UPC-A into EAN-13 by adding a leading `0`; refuse a 13-digit result starting with `2` (FR-007). Stored as `VARCHAR(13)`, unique. Errors are field codes `barcode.invalid` and `barcode.in_store`.
- **Rationale**: FR-006 and FR-007. UPC-A is EAN-13 with a leading zero, so one stored form makes US1-6 hold by construction.
- **Open point for the owner, not built**: GS1 also reserves EAN-13 prefixes `02`, `04` and EAN-8 prefixes `0` and `2` for in-store use, and a UPC-A starting with `2` becomes `02…`. The spec only refuses `2…` 13-digit codes, so the plan does the same. Widening the rule is a spec change for `008` (catalog checking) if the owner wants it.

## R5. Compared form of a name

- **Decision**: One class `NameComparison` builds, from any name, spelling or search text:
  1. Trim; Unicode NFKD through `Normalizer` (`intl` is already in the PHP image).
  2. Remove combining marks (`\p{Mn}`). This drops French accents and Arabic short vowels, shadda and sukun, and turns `أ إ آ` into `ا` (their decompositions are `ا` plus a mark). It also turns `ؤ` into `و` and `ئ` into `ي`, which is wider than the spec's list and is accepted for search and duplicates.
  3. Map `ة → ه`, `ى → ي`, `ٱ → ا`, remove tatweel `ـ`, expand `œ → oe` and `æ → ae` (`œufs` and `oeufs` must match).
  4. Lowercase (`mb_strtolower`).
  5. Every character that is not a letter or digit becomes a space; collapse spaces.
  6. Each word written only in Latin letters and longer than one letter loses one final `s` or `x`.
  The result is the **compared name** (words separated by one space). The **identity key** is the compared name with spaces removed.
- **Rationale**: FR-015 and US3-3 (spaces ignored for "the same name"). Building the form in PHP once, and storing it, keeps MySQL collations out of the rule. Punctuation as space makes `pomme-de-terre` and `pomme de terre` the same.
- **Storage**: compared columns use `utf8mb4_bin`, so MySQL never applies its own case or accent folding, which differs from FR-015 and would make the unique index disagree with the rule.

## R6. Search (FR-014)

- **Decision**: `global_product_terms` holds one row per name and per other spelling of every checked catalog product, with its compared form. A search, at least 2 characters after trimming, is compared as in R5, then matched in MySQL against `global_product_terms.compared` and `shop_products.compared_name` with `LIKE 'q%'` (indexed) or `LIKE '% q%'` (word start) or `LIKE '%q%'`. Each product keeps its best term. Rank: exact, then name start, then word start, then contains; ties put the shop's own products first, then the shorter name, then alphabetical. At most 10. A catalog product the shop already has appears once, carrying both the catalog product and the shop product.
- **Rationale**: Pending catalog products have no term rows, so another shop's typed name can never be suggested (US2-5, SC-005). At pilot scale (hundreds to low thousands of checked catalog products, a few thousand products per shop) scanning the unindexed `LIKE` forms is fast; the term table keeps the query one join.
- **Alternatives**: MySQL `FULLTEXT` with the ngram parser: ranking does not follow FR-015 and Arabic variants still need our form. Meilisearch or Scout: a new service for a list this size. Revisit when checked catalog terms pass about 50 000 rows.
- **Rate limit**: suggestions and barcode lookups share a limiter of 120 requests per minute per account. The app will debounce typing.

## R7. Close names (FR-016)

- **Decision**: For a creation or rename that is subject to the hold, the candidates are the checked catalog terms and the shop's products, without the product being renamed and without the catalog product it is linked to. SQL keeps a candidate if any of these holds on compared forms: its length is within 2 characters of the new name; one contains the other (the shorter one at least 3 letters); they share a word of at least 3 letters (`CONCAT(' ', compared, ' ') LIKE '% word %'`). PHP then keeps the true matches: containment, shared word, or a Levenshtein distance of at most 2 computed over code points (PHP's `levenshtein()` counts bytes, which is wrong for Arabic). Ranking: smallest distance first, then containment, then shared words, then alphabetical; up to 5, merged by product as in R6.
- **Rationale**: Exact to the clarified rule, with SQL only narrowing the set. The minimum of 3 letters for containment matches the word rule and stops a 2-letter spelling from holding every name.
- **Never held**: a creation with a barcode, a creation from a catalog product, and a rename of a product whose catalog product has a barcode (FR-017).

## R8. Same name and same catalog product, under concurrency

- **Decision**: Unique indexes are the final guard, as in 006: `shop_products (shop_id, identity_key)` for FR-017, `shop_products (shop_id, global_product_id)` for FR-011 (MySQL allows several `NULL`s), `global_products (barcode)` and `global_products (translation_key)`. Actions check first to answer with the existing product, then catch `UniqueConstraintViolationException` and answer as if the other request came first, with the same code and `existing_product_id`.
- **Unknown barcode from two shops at once**: the action inserts the pending catalog product inside a nested transaction (a MySQL savepoint). On a unique violation it rolls back to the savepoint, reads the row the other request created, and links to it. The whole creation runs in one transaction, so a shop product refused for its name leaves no pending catalog product behind.
- **Rationale**: Edge cases "two identical creations" and "two shops add the same unknown barcode at the same moment".

## R9. Pending catalog products

- **Decision**: A product created from an unknown barcode gets status `pending`, key `products.barcode_<13 digits>` (fits the FR-001 form), and keeps `pending_name` and `pending_language` from the creating request. It has no name rows and no term rows. The request must send `language` in that case as well as when it sends no name, since FR-004 keeps the typed language. No other verification logic is built (backend guide).
- **Rationale**: FR-001 requires a key on every catalog product. The key changes when the operator file checks the product (R10), so apps must identify catalog products by `id`, never by key.

## R10. Catalog file and `catalog:load`

- **Decision**: The file is JSON, `app/Modules/Catalog/database/catalog/products.json`: a list of `{ "key", "barcode"?, "names": { "fr", "ar", "en" }, "spellings"?: { "fr": [], "ar": [], "en": [] } }`. Latin-script Tunisian spellings (`tmatem`) go under `ar`. The command `php artisan catalog:load {file?}`:
  1. Reads and validates the whole file first: key form, three names present (at most 120 characters after trimming), keys and barcodes unique in the file, barcodes valid and not in-store (R4).
  2. Checks the file against the database: a barcode held by a checked product under another key, a file key already used by another barcode, or a pending barcode whose file key is already taken, stops the load. An existing barcode is never changed; a missing `barcode` in the file leaves the stored one alone.
  3. In one transaction: adds new keys; for a barcode waiting to be checked, turns that same row into a checked one with the file's key and names; updates changed rows in place and rebuilds their term rows; leaves unchanged rows untouched, so a second load changes nothing (SC-006). Keys missing from the file are never deleted.
  4. Prints added, updated and unchanged counts; on error prints the entry position, its key and a reason code, exits non-zero and changes nothing.
- **Rationale**: FR-003, FR-003a, US4. JSON needs no new package. Validating before writing gives "stops with no change" even for checks that need the database.
- **Seeding**: the command is run by hand (quickstart). `DatabaseSeeder` also calls it so `migrate:fresh --seed` gives a usable catalog. Tests use small fixture files, never the real list.
- **First list**: Claude drafts at least 150 entries (vegetables, fruit, bread and pastries, eggs, dairy, dry goods sold loose, spices and similar) with French, Arabic and English names and other spellings; the owner reviews it before the feature closes (spec Assumptions).

## R11. Prices

- **Decision**: `sale_price` required, `purchase_price` optional and nullable, both JSON integers in millimes from 0 to 999 999 999 (999 999,999 DT), stored as unsigned `BIGINT`. A string or a fraction is refused (`sale_price.integer`); above the maximum is `sale_price.too_high`. No check between the two prices.
- **Rationale**: Constitution money rule and spec edge cases. The maximum is a named constant that keeps every later sum far from 64-bit limits; no small shop sells a single item above it.

## R12. Errors with a pointer or matches

- **Decision**: `ApiException` gains an optional `details` array, merged into the error body beside `code`. Duplicate refusals add `existing_product_id`; a hold adds `matches`, up to 5 entries in the suggestion shape (contract).
- **Rationale**: FR-018 and US3-1 need data in the error. Keeping it at the top level matches `retry_after_seconds` from 006.

## R13. Lists

- **Decision**: `GET /products` uses Laravel cursor pagination, ordered by `compared_name` then `identity_key`, 50 per page by default, `per_page` from 1 to 100.
- **Rationale**: The backend guide requires cursor pagination; name order is what a merchant scans for. `identity_key` is unique in a shop, so it breaks ties; the binary `id` cannot, because a cursor is JSON and would carry the raw bytes. An index on `(shop_id, compared_name, identity_key)` serves it (changed during implementation, 2026-11-07).

## R14. Postman collection

- **Decision**: `postman/shop-keeper-006.postman_collection.json` becomes `postman/shop-keeper.postman_collection.json`, one collection for the whole API, with a "Products" folder after the 006 folders. A pre-request script makes a random valid EAN-13 starting with `619` (GS1 Tunisia) so each run starts from an unknown barcode. `ApiCollectionTest` follows the rename, ignores query strings, and maps `{{barcode}}` to `{barcode}` as it maps `{{x_id}}` to `{x}`.
- **Rationale**: US6 asks for "the updated collection" run after the 006 journey. A fixed barcode would be pending on the second run and change the answers.
